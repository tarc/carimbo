D-27 Response cache: key, entry format, modes and on by default in Development and Eval (refines D-19). Phase 3. The cache is a CachingLlmGateway decorator, our own and not a framework cache client. Key: lowercase SHA-256 over canonical JSON with key_version llm-cache-key-1 and the fields model (as sent: alias and dated id are different keys), max_tokens, cache_document (included: it changes the final request and billed usage, so max_repairs 0 and 2 have different initial-attempt keys), prompt_version, repair_prompt_version (repair attempts only), SHA-256 of the prompt text, of the schema string, of the document bytes, the document media type, each follow-up turn's role and text SHA-256, and the replicate salt (empty when absent). Excluded: cache mode, API key, base URL, timeout, retry count, reference date, case id, pricing version. A test forces every new LlmRequest property to be keyed or explicitly excluded. Entry: one file <key>.json per key with entry_version llm-cache-entry-1, written to a temporary file and moved into place; an unreadable or mismatched entry is a miss. Modes off, read_write, read_only, refresh. Only end_turn answers are stored; a refresh that is not end_turn keeps the previous entry. A hit reports the original latency, usage and cost and http_attempts 0. A read_only miss is the typed infrastructure failure kind cache_miss and calls no provider. On by default in Development and Eval (user decision 2026-10-15, matching D-07 and LLM-04, which say enabled in dev and eval): with no Llm:Cache settings the host caches in read_write mode under .cache/llm resolved against the host content root (the process working directory, so <repo>/.cache/llm for every just recipe, which runs from the repo root; .cache/ is git-ignored at any depth). Llm:Cache:Directory overrides the directory (a relative path resolves against the content root) and Llm:Cache:Mode (off, read_write, read_only, refresh) the default mode; off turns the cache off. In every other environment the cache is off, and a non-blank Llm:Cache:Directory or an Llm:Cache:Mode other than off fails startup. Hermetic tests turn the cache off explicitly: the Api test host sets Llm:Cache:Mode off unless a test passes its own cache settings (a per-test temporary directory), and the e2e scripted host gets a per-test Llm__Cache__Directory. Consequence: a run whose truncated or refused attempts were never cached replays those cases as cache_miss; faithful re-grading of them comes from the stored JSONL (EVAL-02), and the Phase 6 discuss must decide whether its replay set (CI-02) accepts that. Rejected: the built-in distributed-cache chat client (no control of the key, no original cost), opt-in only by Llm:Cache:Directory with no default directory (the research recommendation, overridden by the user on 2026-10-15: the brief makes the response cache mandatory for dev and eval reruns, so a default run must not pay twice; the test order-dependence it guarded against is handled by tests turning the cache off explicitly), caching every non-error answer (a replay could turn a typed failure into a graded answer).

D-28 One retry owner: the SDK, MaxRetries 2 (refines D-21). Phase 3. The Anthropic SDK retry is the single policy (408, 409, 429, 5xx and connection errors, backoff with jitter, honouring retry-after, retry-after-ms and x-should-retry; other 4xx are not retried). Llm:Anthropic:MaxRetries defaults to 2 and is bounded 0 to 5 at startup. No Polly, no Microsoft.Extensions.Http.Resilience and no hand-written retry handler; tests show 1 + MaxRetries attempts through the composed chain and a static test rejects resilience packages. Worst case for one case with defaults is (max_repairs + 1) times (MaxRetries + 1) times the 300 s per-attempt timeout, 2700 s, so the runner's read timeout becomes 2700 s; an abandoned request is cancelled server-side through the request-aborted token and charged at the reserve. Rejected: a custom retry loop with MaxRetries 0 (re-implements Retry-After and x-should-retry), keeping MaxRetries 0 (transient 529s become infrastructure failures in measured runs).

D-29 Eval contract 3: per-request overrides, cache block and incurred cost (refines D-24, and D-23 on the repair budget). Phase 3. Request and response carry contract_version "3"; "2" is refused. The request gains an optional overrides object with model (must be priced by the pricing table), prompt_version (from the prompt catalog), max_repairs (integer 0 to 5), cache_mode (off, read_write, read_only, refresh; anything but off needs a host whose cache is on) and replicate_salt (1 to 64 characters of A-Z, a-z, 0-9, dot, underscore, hyphen); an invalid value is HTTP 400 naming overrides.<field> without echoing it, and an unknown member is HTTP 400 body. effective gains cache_mode and replicate_salt, and model, prompt_version and max_repairs echo the resolved per-request values. Each attempt gains cache {mode, status hit|miss|refresh, key, stored} (null when no cache was consulted) and incurred_cost_usd ("0.00000000" for a hit or a cache_miss failure, equal to cost_usd otherwise, null when unknown); the response gains a top-level incurred_cost_usd. cost_usd stays the notional cost (the original cost on a hit). The runner writes record_version 3 with request.overrides, caps spend on incurred cost, and refuses to resume a run with different overrides; summaries (summary_version 3) report incurred and notional cost and the cache hit rate. Rejected: additive fields under "2" (cost_usd changes meaning on a hit, so consumers must opt in, the D-24 rule), per-request overrides without validation (an unpriced model would spend with a null cost).

D-30 Prompt catalog (EXT-05). Phase 3. Prompt texts live in a PromptCatalog in Carimbo.Extraction: extract-003 is the default and extract-002 is restored byte-exact from the commit before 44c4323 as a second selectable version (assumption A4: it has the known label defects G-02-1 and G-02-2 but is schema-compatible, and it makes the prompt_version override and a two-prompt comparison real). Each text is pinned by SHA-256 in tests; the repair prompt stays repair-001. The prompt version is part of the cache key and of effective and attempts[] metadata. Only catalogued versions can be selected; no prompt text crosses the HTTP boundary. Rejected: a test-only prompt version (the override would have no real effect), free prompt text in the request.

D-31 Model-call spans and the local trace viewer (refines D-17). Phase 3. TracingLlmGateway is the outermost gateway decorator (Tracing over Caching over CostAccounting over the adapter), so every CompleteAsync call, a cache hit included, is one span named "chat <model>" of kind client from the ActivitySource Carimbo.Llm. Attributes are an allowlist owned as constants in LlmTelemetry.cs: GenAI semantic-convention names (operation, provider anthropic, request model and max tokens, response model, id and finish reasons, usage tokens with gen_ai.usage.input_tokens summing every input class), plus carimbo.llm.* for cost (decimal string, 8 places), pricing version, cost warning, cache status and mode, http_attempts, prompt version and replicate salt, and error.type on failure. No prompt, response, schema, document or key ever goes into a span, and exceptions are not recorded as events. The GenAI conventions are status Development with no release, so the pin is the constants file plus the allowlist test, citing open-telemetry/semantic-conventions-genai and the date read. The Api always registers OpenTelemetry tracing with the ASP.NET Core server instrumentation and the Carimbo.Llm source; the OTLP exporter is added only when OTEL_EXPORTER_OTLP_ENDPOINT is set. The tracer provider uses the AlwaysOn sampler set in code: every request is recorded whatever the inbound traceparent's sampled flag (an inbound trace id is still continued), and OTEL_TRACES_SAMPLER has no effect because the SDK gives a sampler set in code precedence, so the trace id an eval response reports always names a trace holding its model-call spans; whether spans leave the process is decided by the exporter setting alone. No HTTP client instrumentation (it would add one span per HTTP attempt; http_attempts is a tag instead). The viewer is Jaeger v2 from compose.yaml on loopback, in-memory. Rejected: Microsoft.Extensions.AI UseOpenTelemetry (the gateway is not an IChatClient, D-21), a collector in Milestone 1, cost as a double attribute, the SDK default parent-based sampler (an inbound traceparent with flags 00, or a ratio sampler from OTEL_TRACES_SAMPLER, leaves a reported trace id with no model-call spans, measured with OpenTelemetry 1.19.1 on 2026-10-15).

D-32 Golden eval-response fixtures (API-04). Phase 3. GoldenResponseTests in Carimbo.Api.Tests posts a fixed scenario matrix through the real endpoint with scripted gateways and writes data/contract/eval-responses/<scenario>.json (indented, LF, endpoint latency_ms normalised to 0). In normal runs the test compares bytes and fails with "Run: just golden"; CARIMBO_UPDATE_GOLDEN=1 (just golden) rewrites them. The files are generated and never hand-edited. Strict Pydantic models in carimbo_evals/contract.py (extra forbid) parse every fixture in pytest, so a renamed or added .NET field fails CI. data/contract/eval-request.json is a hand-written contract 3 request that the .NET test posts and the runner's payload builder must reproduce. Rejected: generating Pydantic response models from a response JSON Schema (no exporter exists; strict hand models plus fixtures cover the contract with far less machinery), a separate golden-check recipe (the compare-mode test already fails just dotnet-check).

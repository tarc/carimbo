This plan's slice: **As a** developer, **I want to** read the labelling rule, the loop semantics, the decision-1 contract and the cache v2 rules as recorded decisions before any code implements them, **so that** every later plan and every reviewer works from one written source.

`## D-34 Decision cases and the labelling rule (refines D-14 and D-26)` — Decision: a decision case starts from a committed extraction outcome (status, invoice when present, validator findings), never from a PDF, so only the agent is measured; cases are generated by `dotnet/tools/DecisionCases` from specs kept in code (a skeleton base case mapped by NfeXmlMapper, a mutation, a forced status for typed failures), validated by the real InvoiceValidator at the skeleton as_of_date, and written to `data/decision/` (cases/<case_id>.json, policy.json, manifest.json, expected.json), with `just decision-cases-check` failing on any byte difference; case ids are neutral (dc-001 to dc-008) so the id the model sees never names its label; the buyer policy is one generated policy.json with `buyer_cnpj` (a synthetic alphanumeric CNPJ with valid check digits) and `approval_limit` (money string "200000.00"); labelling rule `decision-labels-1` is ordered, first match wins: 1 extraction status other than success -> escalate, cause extraction_not_success; 2 recipient tax_id other than buyer_cnpj -> reject; 3 any warning finding -> escalate, cause policy_warning; 4 totals.invoice_total strictly greater than approval_limit -> escalate, cause over_limit (a total equal to the limit is not over it); 5 otherwise approve; approve and reject carry cause none; `DecisionRules.Label` in Carimbo.Decisions is the single implementation, the generator labels every case with it and the agent prompt states the same list in prose; labels live only in expected.json and case intents only in manifest.json, and the Tools host reads neither; the eight cases are one per rule path: approve on a Simples invoice, approve on a Regime Normal invoice, reject (recipient not the buyer), escalate on a TAX_CODE_UNSUPPORTED warning, escalate over the limit, escalate on validation_failed, escalate on a typed extraction failure (refused), and the ordering trap (recipient not the buyer and over the limit -> reject); step-budget exhaustion and tool failure are runtime faults injected by offline tests, not dataset cases; reversibility: case bytes feed tool results and so every agent cache key, and the rule order fixes every label, so a change is a new labelling version. Rejected: hand-written case files (findings could disagree with the validators); descriptive case ids (the id would leak the label); labels inside served case files (one tool call away); starting from PDFs (extraction misreads would blur decision accuracy and every live run would pay for extraction).

`## D-35 Tools host and agent loop (refines D-08, D-09 and D-10)` — Decision: a separate Carimbo.Tools process (ModelContextProtocol.AspNetCore 2.2.0) serves four read-only MCP tools over Streamable HTTP at /mcp, HttpServerSessionMode.Stateless, default URL http://127.0.0.1:5090, AllowedHosts restricted to loopback names, reading `Tools:CasesDirectory` (default data/decision) and never writing: get_extraction_status(case_id), get_invoice(case_id), get_validator_findings(case_id), get_policy(); an unknown or malformed case id is a tool error, a case without an invoice answers normally with invoice null; it has no compose service and is started as a process by the recipes and tests, like the Api. The agent is Carimbo.Agent, a hand-written loop inside the Api: an MCP client per run (Agent:ToolsUrl, default http://127.0.0.1:5090/mcp, loopback only) that refuses a listed tool whose ReadOnlyHint is not true; one step is one model call; Agent:MaxSteps is configuration only, 1 to 10, default 6, echoed as effective.max_steps; every request carries the pinned system prompt agent-001 (the D-34 policy in prose), a first user turn of exactly `case_id: <case_id>` then a newline and the task sentence, the four tools, and the Decision model-facing schema as output_config.format, with no tool_choice and no sampling parameters; an answer without tool calls is the final answer, parsed strictly with Wire.Options plus Decision.NullViolations plus the outcome-cause rule (approve and reject carry cause none; escalate carries extraction_not_success, policy_warning or over_limit; every other pair is schema_invalid); D-38 records whether the live probe confirmed this structured-output path, and a probe that rejects tools combined with output_config.format makes phase decision D-13's strict local submit_decision tool (input schema the Decision, tool_choice auto) the path, adopted through a re-planning gate on the agent loop, endpoint and e2e plans before they run; the tool calls of one answer run in block order and their results return in one user message; a tool failure (MCP error result, unknown tool, transport failure or timeout, while listing, during the loop or in the guard) ends the run at once with a code decision escalate / tool_failed, no retry, the tool name and error kind recorded; a tool_use answer on step MaxSteps ends with escalate / step_budget_exhausted and its tools are not run; a model refusal, max_tokens, an unparseable or schema-violating Decision, an outcome-cause pair outside the rule, a tool_use answer with no tool call, and any gateway failure including cache_miss are typed failures (status refused, truncated, schema_invalid or infrastructure_failure) with no decision, never escalate causes; after a parsed model decision the guard calls get_extraction_status itself (source guard, not a model step, not citable), and when the status is not success the final decision is the guard's escalate / extraction_not_success, with guard.overridden true when the model said approve or reject and the model's own decision kept as model_decision; code-made decisions carry a fixed reason and no evidence; one Decision type {evidence, reason, outcome, cause} whose cause enum includes the code-only values, the prompt allowing the model none, extraction_not_success, policy_warning and over_limit and the parse boundary enforcing the pairs; default model claude-haiku-4-5, and any priced model may be chosen by override because assistant turns echo thinking blocks (D-37; D-38 records whether the echo was verified live); nothing executes a Decision: it is returned and recorded only. Rejected: an agent framework or the IChatClient tool loop (D-08, D-21); passing tool errors back to the model (deferred by the phase discussion); escalating on model failures (would mix model reliability into decision accuracy, against EXT-02 and EVAL-04); trusting the model to have fetched the status (it may answer on its first turn); a separate model-facing draft type (two schemas and two generated models for one prompt rule); a per-request max_steps (deferred).

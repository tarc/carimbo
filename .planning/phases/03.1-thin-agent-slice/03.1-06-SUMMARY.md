# Phase 3.1 Plan 06: a stateless MCP Tools host serves the cases read-only Summary

**A separate Carimbo.Tools host serves get_extraction_status, get_invoice, get_validator_findings and get_policy over stateless Streamable HTTP in catalog order, loopback-only, and a real McpClient lists and calls each one while tests prove nothing can be written, steered out of the case directory or served to a foreign Host.**

## Performance

- **Duration:** about 10 min
- **Completed:** 2026-10-22
- **Tasks:** 2 (1 tracer, 1 auto), both TDD
- **Files:** 7 created, 2 modified

## Accomplishments

- `CarimboTools.CreateApp` is the composition root: default URL `http://127.0.0.1:5090` (applied only when neither `urls` nor Kestrel endpoints are configured), `AllowedHosts` defaulted to `127.0.0.1;localhost;[::1]`, `Tools:CasesDirectory` (default `data/decision`) resolved against the content root and checked for `cases/` and `policy.json` (startup fails with an `InvalidOperationException` that names the key but not the path), `/mcp` stateless Streamable HTTP and `/healthz`.
- `CaseTools` has four methods, each `[McpServerTool(Name = CaseToolCatalog.X, ReadOnly = true, Idempotent = true, Destructive = false, OpenWorld = false)]` with the catalog description, returning the catalog rendering of `CaseStore.Load` or `LoadPolicy`. `InvalidCaseIdException` becomes `McpException("invalid case id")` and `CaseNotFoundException` becomes `McpException("unknown case <id>")`.
- 21 tests in `Carimbo.Tools.Tests` run an in-process host (TestServer) with a real `McpClient`, plus one Kestrel test on a free loopback port.
- The RED evidence of the tracer: before `CaseTools` existed, the two target tests failed with `McpProtocolException: Method 'tools/list' is not available` / `'tools/call'` (the host served no tools); the third test (null session id) already passed, as it should.

## Pinned tool list

- **Rendering rule:** for each tool in served order, `name` + LF + `description` + LF + `JsonSchema.GetRawText()`; the four per-tool renderings joined with LF; SHA-256 over the UTF-8 bytes.
- **Derivation (outside the code under test):** Python `hashlib.sha256` over strings typed by hand from `CaseToolCatalog` and the schema shapes RESEARCH Pattern 1 records: `{"type":"object","properties":{"case_id":{"description":"The case id, for example dc-001.","type":"string"}},"required":["case_id"]}` for the three case tools and `{"type":"object","properties":{}}` for `get_policy`.
- **Value:** `8d4fb66f4eeba53d13c5473f5419227b98b9836dd2055fc368cc11da6a41cd68`.
- The served list matched the hand-written rendering on the first run, so there was no SDK serialization difference to record. A mutation of one description word (BRL. to BRL!) made the pin test fail, then was reverted.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The SDK served the tools in hash order, not catalog order**
- **Found during:** Task 1, first GREEN run
- **Issue:** `WithTools<CaseTools>()` put the tools in a hash-ordered collection; `get_invoice` came first on six consecutive runs, so `tools/list` did not follow `CaseToolCatalog` order (the plan's ordering edge, and part of every agent cache key, D-37). A `WithListToolsHandler` alone cannot fix it: the SDK lists the collection first and appends the handler's tools (it produced duplicates when tried).
- **Fix:** `CreateTools()` builds the four tools with `McpServerTool.Create(method, ...)` in catalog order, resolving each method by its `[McpServerTool]` name; `WithListToolsHandler` returns their `ProtocolTool`s and `WithCallToolHandler` dispatches by name (unknown name: `McpProtocolException`, InvalidParams). The tools are still the SDK's own `McpServerTool` instances, so argument binding and the McpException-to-IsError mapping are unchanged.
- **Files modified:** dotnet/src/Carimbo.Tools/Program.cs
- **Verification:** the list-order test, the pinned-SHA test and the unknown-tool test pass.
- **Commit:** `080b3d0`

### TDD notes

- **Task 2 had no RED phase.** The behaviors in Task 2 were all already satisfied by Task 1's implementation (the host was written against the edge list), so all 11 new tests passed on first run: an unexpected green. Instead of trusting them, five mutations were applied and reverted: `DefaultAllowedHosts = "*"` (Kestrel test failed), `ReadOnly = false` on `get_policy` (two tests failed), a description edit (pin test failed), a path appended to the invalid-id error (nine theory cases failed) and a tool that touches `policy.json`'s last-write time (directory snapshot test failed). All five were detected, so none of the new tests is vacuous. There is no separate `feat` commit for Task 2 because no production code changed.
- **RED evidence is semantic only.** `gsd_run check tdd-red-evidence` supports TAP, JUnit XML, swift-testing, unittest and go test reports; xunit.v3 on Microsoft.Testing.Platform prints none of those, so no machine verdict was recorded. The semantic assessment is above: the target tests executed and failed because the host served no tools.

**Total deviations:** 1 auto-fixed (Rule 1). **Impact:** the served order is now guaranteed by construction instead of by hash luck; the public behavior in the plan is unchanged.

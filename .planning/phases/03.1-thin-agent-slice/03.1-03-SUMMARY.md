# Phase 3.1 Plan 03: generated decision cases and the labelling rule Summary

**Carimbo.Decisions with a path-safe read-only CaseStore and the single DecisionRules implementation of decision-labels-1, plus a DecisionCases generator that writes eight synthetic dc-NNN cases (real validator findings over the skeleton) with a byte-identity gate in `just check` and CI.**

## Accomplishments

- DecisionRules.Label applies the five ordered rules (status, recipient, warning, strict over-limit, approve); a total equal to the limit approves and limit + 0.01 escalates over_limit.
- Eight cases, one rule path each: dc-001 approve (Simples), dc-007 approve (Regime Normal), dc-004 reject (recipient is another company), dc-002 reject (ordering trap: CPF recipient and 3190646.05 over the limit), dc-003 escalate/policy_warning (TAX_CODE_UNSUPPORTED, zero errors), dc-006 escalate/over_limit, dc-008 escalate/extraction_not_success (validation_failed with ITEM_ARITH and TOTAL_SUM_PRODUCTS errors), dc-005 escalate/extraction_not_success (refused, no invoice).
- The generator renders everything in memory, so `--check` compares the whole directory and reports `stale:` for changed, missing and extra files; verified by hand with a one-byte edit and a stray file.
- A spec's intended label only self-checks: `DecisionCases` exits 2 naming the case and both labels when the rule disagrees, and never writes an intended label.
- Label-leak guard on the data side: every case file holds exactly case_id, extraction, invoice and findings, and a walk at any depth finds no label, intent, decision, cause or labelling_version member and no "decision-labels" text.
- Buyer policy: `CARIMBO0000177` (base CARIMBO00001 with computed check digits), limit `200000.00`.

### Locked Decisions

(Local numbering D-01..D-19 is this phase's; "DECISIONS D-xx" is `docs/DECISIONS.md`. Copied verbatim from `03.1-CONTEXT.md` `## Implementation Decisions`.)

**Carried forward (locked earlier, not re-discussed)**
- DECISIONS D-08: a hand-written loop (call model, run tool, append result, repeat) with a step budget, and no agent framework (no Semantic Kernel, no Microsoft Agent Framework).
- DECISIONS D-09: the MCP tools are read-only. The agent outputs a `Decision`. Executing it is not a tool and does not happen in Milestone 1.
- DECISIONS D-10 and D-26: step-budget exhaustion, a failed tool call and an extraction outcome other than success escalate. The near-duplicate trigger stays in Milestone 2.
- Stack: `ModelContextProtocol.AspNetCore` 2.2.0 (with `ModelContextProtocol` 2.2.0 exact), a separate `Tools` host, Streamable HTTP, stateless, `AllowedHosts` set explicitly.
- Structured outputs only. No forced `tool_choice`, no `Temperature`/`TopP`, no prefill (they return 400 on the current models).
- DECISIONS D-27 and D-28: the response cache is on by default in Development and Eval, and the SDK is the only retry owner (`MaxRetries` 2). DECISIONS D-31 and D-33: one costed `chat <model>` span per model call, with no content.
- Live calls go only through capped `just` recipes: US$1.00 per run and US$5 per phase. CI has no provider key. All data is synthetic (DECISIONS D-14).
- Wire conventions: snake_case, string enums, money as `^-?[0-9]+\.[0-9]{2}$` strings. Generated files are never hand-edited.

**Case input and tool data**
- **D-01:** A decision case starts from a **committed extraction outcome**: extraction status, invoice (when present) and validator findings. It does not start from a PDF. Only the agent is measured, so extraction misreads (such as the live case-002 access key) never blur decision accuracy, and a live run pays only for agent calls.
- **D-02:** The `Tools` host reads the cases from a **read-only case directory** (default `data/decision/`, configurable), keyed by `case_id`. It never writes. The request names the case, and the tools read it from disk.
- **D-03:** Four narrow read-only tools: `get_extraction_status(case_id)`, `get_invoice(case_id)`, `get_validator_findings(case_id)` and `get_policy()` (see D-06). The agent chooses what to call, so the recorded tool calls mean something. An unknown `case_id` is a tool failure.
- **D-04:** The case outcome files are **generated, not hand-written**. A small spec per case (a base skeleton invoice, a mutation, and a forced status for non-success cases) feeds a .NET generator that runs the real `Carimbo.Validation` validators. The findings are therefore real, and the expected label is computed by the D-09 rule. The output is committed with a staleness check, following the `just datagen-check` / `just golden` pattern, and it joins the generated-files list in AGENTS.md. — **Reversibility:** costly — once cached live runs exist, the case bytes feed the tool results and so the response-cache keys; regenerating different bytes invalidates the replay.
- **D-05:** The first user turn gives **only the `case_id` and the task**. The agent has to call tools to learn anything.

**Decision policy and labels**
- **D-06:** Reject grounds come from **one committed buyer policy file** (our company's CNPJ and an approval limit in BRL; the planner may add a field only if a case needs it), served by `get_policy`. The values are synthetic.
- **D-07:** A **warning** on an otherwise successful extraction (e.g. `TAX_CODE_UNSUPPORTED`) leads to **escalate**.
- **D-08:** A total **over the approval limit** on an invoice addressed to us leads to **escalate**, not reject.
- **D-09:** The labelling rule is an **ordered, first-match rule list**. It is recorded as a new decision in `docs/DECISIONS.md`, and the case generator computes each expected label from the same list. The agent prompt states the policy in prose.
  1. extraction status ≠ `success` → escalate (cause `extraction_not_success`)
  2. recipient `tax_id` ≠ our CNPJ → reject
  3. any warning finding → escalate (cause `policy_warning`)
  4. `totals.invoice_total` > approval limit → escalate (cause `over_limit`)
  5. otherwise → approve

  — **Reversibility:** costly — expected labels, committed cases and graded runs all depend on the order; a change is a new labelling version.

**Loop and escalation guards**
- **D-10:** **The model decides, then a deterministic code guard overrides.** After the model returns its decision, the guard checks the case's extraction status. If the status is not success and the model said approve or reject, the final decision becomes escalate with cause `extraction_not_success`. The record carries `guard.overridden = true` and the model's original decision, so how often the model would have broken policy is measured too.
- **D-11:** A **tool failure** (MCP error, Tools host unreachable, unknown case) **ends the loop in escalate at once**, with cause `tool_failed` and the tool name and error recorded. There is no retry inside the loop (DECISIONS D-28's single retry owner covers only the model SDK).
- **D-12:** **Step-budget exhaustion** ends in escalate with cause `step_budget_exhausted`. One step is one model call. The budget is set by configuration `Agent:MaxSteps` only (bounded, e.g. 1..10, default **6**, validated at startup like `Extraction:MaxRepairs`) and is echoed in the response's effective config. There is no per-request override.
- **D-13:** The final `Decision` arrives as **structured output on the final turn**. Tools stay available, and the response format is the Decision JSON Schema exported from a new Domain record through the same `Wire.Options`, schema export and Pydantic codegen chain as `Invoice`. A turn with no tool calls is the final answer. **Spike first:** confirm that tools and `output_config.format` combine on `claude-haiku-4-5`. If they don't, fall back to a strict local (non-MCP) `submit_decision` tool whose input schema is the Decision, under `tool_choice` auto, and record which path was chosen as a decision. — **Reversibility:** costly — the Decision schema is committed and generated into Pydantic, and the grader reads its fields.
- **D-14:** `evidence` is a list of **structured citations** `{source, ref, value}`: `source` is a tool name, `ref` is a field path or rule id (e.g. `get_invoice` / `recipient.tax_id`, `get_validator_findings` / `TAX_CODE_UNSUPPORTED`), and `value` is the cited value as a string.
- **D-15:** The default agent model is **`claude-haiku-4-5`**, as for extraction. `overrides.model` can still pick another model the pricing table knows.

**Eval contract and grading**
- **D-16:** A **new route, `POST /eval/decisions`**, with its own contract version (e.g. `decision-1`). It uses the same auth and the same Development/Eval-only gating as `/eval/extractions`. The request carries `case_id` plus the overrides that apply (`model`, `cache_mode`, `replicate_salt`; the planner decides on `prompt_version`). The response carries the final decision, reason, evidence, cause, guard info, effective config (`max_steps`, model, prompt version), each step (model call usage, cost, stop reason, tool calls with name, arguments, outcome), token and cost totals (incurred vs notional, as in contract 3) and `trace_id`. Extraction contract 3 and its golden fixtures stay untouched. — **Reversibility:** costly — a published wire contract that the runner, grader and stored JSONL read.
- **D-17:** The offline grader scores:
  - **primary:** the decision matches the expected label
  - **secondary:** the escalation cause matches when the expected decision is escalate, and every evidence citation's `source` is a tool actually called in that case's run

  It also reports steps, tool-call counts, guard overrides, tokens, cost and latency. Everything is deterministic, with no LLM-as-judge (DECISIONS D-16).
- **D-18:** About **8 committed cases, one per rule path**: approve ×2 (Simples and Normal), reject (recipient is not us), escalate on a warning, escalate over the limit, escalate on `validation_failed`, escalate on a typed failure (refused or schema_invalid), and one ordering trap (recipient not us AND over the limit → reject per D-09). Each case derives from a skeleton invoice. Budget exhaustion and tool failure are runtime faults, so offline tests inject them and they are not dataset cases.
- **D-19:** The harness reuses `carimbo_evals`: a `decisions` subcommand on the same runner (bounded concurrency, cost cap, resume, JSONL, overrides check on resume), a decision request builder, and a separate decision grader and summary module. `just decisions [max_cost] [cache_mode]` makes the live run (US$1.00 default cap, `read_only` replays for free), and an e2e test in `just check` runs the cases against the scripted host.

## Summary

The phase is mostly an extension of seams Phase 3 already built, plus two genuinely new pieces (the MCP Tools host and the tool-use loop). Everything the CONTEXT asks for is feasible with the pinned stack. I executed three scratch spikes this session: (1) a `ModelContextProtocol.AspNetCore` 2.2.0 stateless server with an `McpClient` over Streamable HTTP, both in-process (TestServer) and over real Kestrel with `AllowedHosts`; (2) the Anthropic 12.53.0 SDK building a request that carries `tools`, `output_config.format` and `tool_use`/`tool_result` history, and parsing a `stop_reason: tool_use` response; (3) the Domain schema exporter on a decision-shaped record. The findings change a few things the CONTEXT left open (below).

The central design problem is the response cache. Today `CachingLlmGateway` stores only `end_turn` answers and the key has no notion of tools or tool turns, so a tool-use loop would never replay. The recommended fix: add `LlmStopReason.ToolUse`, store `tool_use` answers too (with their tool calls), and key every call on the full conversation so far including tool definitions and tool results. Because the tool results come from committed, byte-stable case files, every call in the loop gets a stable key and the whole run replays from cache at US$0. To keep Phase 3's cached extraction runs replayable (AGT-06 and the committed README replay command), requests that use none of the new features must keep the exact `llm-cache-key-1` canonical JSON (the pinned `CacheKeyTests` hex stays green); only tool/no-document requests use a new `llm-cache-key-2` shape.

Three non-obvious facts the plan must absorb: (a) a nullable enum property exports as the schema literal `true` with the current `CanonicalSchema` transform, so the Decision `cause` must not be `EscalationCause?` (use a required enum with a `none` member, or extend the transform); (b) the deterministic guard cannot rely on the model having called `get_extraction_status`, so it must fetch the status itself over MCP after the model answers; (c) the Tools host must be running during a cache replay, because tool results feed the next request's cache key.

**Primary recommendation:** add `Carimbo.Tools` (Sdk.Web, `ModelContextProtocol.AspNetCore` 2.2.0) and `Carimbo.Agent` (loop + MCP client over `ModelContextProtocol` 2.2.0, behind a small `IAgentToolbox` interface), grow `LlmRequest`/`LlmResponse` with additive tool-use members and a conditional `llm-cache-key-2`, serve `POST /eval/decisions` from the Api with contract `decision-1`, and make Wave 0 a live-gated probe of tools + `output_config.format` on Haiku 4.5 (the user must supply a key; none is present here).

### Pattern 1: Stateless MCP Tools host and client (verified)

**What:** One `Sdk.Web` host exposing four read-only tools; the Api talks to it with `McpClient` over `HttpClientTransport`.
**When to use:** AGT-01, and every test that lists/calls tools.

Verified behaviours (all executed against 2.2.0 in a scratch project, then re-run over real Kestrel):
- Stateless is explicit and warning-free: `.WithHttpTransport(o => o.SessionMode = HttpServerSessionMode.Stateless)`. `Stateless = true` also compiles (a proxy over `SessionMode`) but prefer the enum. The client reports `SessionId` as null [VERIFIED: spike output `session id: (none)`].
- `[McpServerTool(Name = "get_invoice", ReadOnly = true, Idempotent = true, Destructive = false, OpenWorld = false)]` surfaces as `ProtocolTool.Annotations.ReadOnlyHint == True` on the client [VERIFIED: spike]. These hints are advisory only; "no tool changes state" must be enforced by construction and a test, not by the attribute.
- Tool classes take constructor dependencies from DI (`WithTools<CaseTools>()`, `CaseTools(Dep dep)`) [VERIFIED: spike printed the injected value].
- `ListToolsAsync()` returns `McpClientTool` with `.Name`, `.Description`, `.JsonSchema` (JSON text such as `{"type":"object","properties":{"case_id":{"description":"The case id","type":"string"}},"required":["case_id"]}`) and `.ProtocolTool`; a no-argument tool has `{"type":"object","properties":{}}` [VERIFIED: spike].
- Error mapping: a tool that throws `McpException("unknown case 'nope'")` returns `IsError = true` with text `An error occurred invoking 'get_invoice': unknown case 'nope'`. A missing required argument also returns `IsError = true` with the generic text `An error occurred invoking 'get_invoice'.`. An unknown tool name makes the client throw `McpProtocolException: Request failed (remote): Unknown tool: 'nope_tool'`. A closed port makes `McpClient.CreateAsync` throw `System.Net.Http.HttpRequestException: Connection refused`. On success `IsError` is `null`, not `false`: treat only `IsError == true` as failure [VERIFIED: spike output lines `UNKNOWN`, `MISSING-ARG`, `NOTOOL`, `OK isError=`, and the `down` project].
- `AllowedHosts` set in configuration makes a request with `Host: evil.example` return HTTP 400 over Kestrel [VERIFIED: spike `EVILHOST status=400`]. Whether the SDK also validates `Origin` is not known [ASSUMED]; loopback binding plus `AllowedHosts` is the control.
- In-process: `builder.WebHost.UseTestServer()`, `app.GetTestClient()` passed as `new HttpClientTransport(options, httpClient, ownsHttpClient: false)`; `TransportMode = HttpTransportMode.StreamableHttp` [VERIFIED: spike].
- `McpClient.CreateAsync` per agent run is cheap and stateless; create it per request behind the toolbox, so a host restart cannot leave a stale session.

### Pattern 2: The hand-written loop (algorithm and terminal states)

Loop (one step = one `CompleteAsync` call, D-12):

```
tools = toolbox.ListTools()                    // failure -> ESCALATE tool_failed (steps = 0)
turns = []                                      // alternating assistant / user, ends on user
for step in 1..MaxSteps:
   resp = gateway.CompleteAsync(request(tools, schema, turns))
   record step (usage, cost, stop, cache info, latency)
   switch resp.StopReason:
     ToolUse:
        if step == MaxSteps: break -> ESCALATE step_budget_exhausted      // do not run tools past the budget
        results = []; for call in resp.ToolCalls (in order):
             r = toolbox.Call(call)             // transport error | IsError==true | unknown tool -> ESCALATE tool_failed, stop
             results.add(r)
        turns += assistant(resp.Text, resp.ToolCalls); turns += user(toolResults)
     EndTurn:  parse Decision strictly (Wire.Options) -> done, else typed failure
     Refusal | MaxTokens | Other | gateway exception: typed failure (see Open Question 2)
guard(): status = toolbox.Call(get_extraction_status)  // source=guard; failure -> ESCALATE tool_failed
         if status != success: final = escalate, cause = extraction_not_success;
              guard.overridden = (model outcome != escalate); keep model's original decision and cause
```

Rules that fall out of verification:
- Every `tool_use` block in an assistant turn needs exactly one `tool_result` in the next user message, all in a single user message; a failed tool still needs a result (docs: "return `tool_result` with `is_error: true`") [CITED: claude-api skill, Tool Use Patterns]. Because D-11 ends the loop on failure, the half-built turn is discarded, never sent.
- Do not execute tools requested on the last allowed step; otherwise "one step per model call" and "budget exhausted" disagree.
- Parallel tool calls: allow them (the model will batch `get_invoice` + `get_validator_findings`); execute sequentially in block order (determinism for traces and cache keys); the step count is unchanged.
- The guard's own `get_extraction_status` call is recorded in the response with `source: "guard"` and must not count as a tool the model called, otherwise D-17's "every citation's `source` is a tool actually called" would be satisfiable by citing the guard's call. The guard is needed because the model is not obliged to call `get_extraction_status` at all (docs say the model "may call the tool first (tool_use) or respond with JSON", so the very first turn can already be an `end_turn` JSON answer).
- When status != success the guard sets the final cause to `extraction_not_success` even if the model chose `escalate` with some other cause, otherwise the cause grade (D-17) depends on model wording. Record both `guard.overridden` (outcome changed) and the model's original decision and cause.
- Prompt must say: call the tools first, never answer from memory; cite only tools you called. Do this in the pinned prompt (agent-001), not by forcing `tool_choice` (400).

### Pattern 3: Growing the gateway contract additively

Current seam (read this session): `LlmRequest(string Model, int MaxTokens, string Prompt, LlmDocument Document, string OutputSchemaJson)`, `FollowUps` of text-only `LlmTurn(Role, Text)`, `LlmStopReason { EndTurn, MaxTokens, Refusal, StopSequence, Other }`, `LlmResponse(Text, StopReason, ...)`.

Recommended additions (all additive; existing extraction call sites compile):
- `LlmRequest.Document` becomes `LlmDocument?`; adapter throws only when a document is present and not PDF. `OutputSchemaJson` stays required (the agent always sends the Decision schema).
- `LlmRequest.System` (string?, keyed): stable pinned instructions (policy in prose, tool-first rule) live here; the first user turn holds only the case id and task (D-05). `PromptVersion` carries `agent-001`.
- `LlmRequest.Tools` : `IReadOnlyList<LlmToolDefinition>` (`Name`, `Description`, `InputSchemaJson`), keyed by name + SHA-256 of description and schema, in order.
- `LlmTurn` gains init-only `ToolCalls` (assistant turns: `Id`, `Name`, `InputJson`) and `ToolResults` (user turns: `ToolUseId`, `Content`, `IsError`). The existing alternation rule in `ValidateFollowUps` (assistant, user, ..., ends on user) still holds.
- `LlmResponse.ToolCalls` (init, default empty) and `LlmStopReason.ToolUse` (add at the end of the enum; the cache stores stop reasons by snake_case name, so `tool_use` round-trips through `StopReasonToWire/FromWire` with no change).
- Adapter mapping, all confirmed by the compiled request in the spike: `Tools = [new Tool { Name, Description, InputSchema = new() { Properties, Required } }]`; assistant turn blocks `TextBlockParam` + `ToolUseBlockParam { ID, Name, Input }`; user turn `ToolResultBlockParam { ToolUseID, Content = string, IsError }` (set `IsError` only when true; the SDK emits `"is_error":false` when set); response parse `block.TryPickToolUse(out ToolUseBlock)` giving `ID`, `Name`, `Input` (`IReadOnlyDictionary<string, JsonElement>`); `message.StopReason?.Raw() == "tool_use"` [VERIFIED: executed spike with a capture handler]. Request body observed: `{"model":"claude-haiku-4-5","max_tokens":2000,"output_config":{"format":{"type":"json_schema","schema":{...}}},"tools":[{"name":...,"input_schema":{"type":"object","properties":{...},"required":[...]}}],"messages":[...tool_use...,...tool_result...]}`.
- `InputSchema` in the SDK models only `type`, `properties` and `required`. Keep the tool input schemas that simple (one `case_id` string) and have a test that fails if an MCP tool schema carries other top-level keywords that would be silently dropped.
- Thinking blocks: Haiku 4.5 does not think by default, so a tool turn has no thinking block to echo. Models that think by default (for example `claude-sonnet-5-5`, which the pricing table knows and `overrides.model` would therefore accept) return thinking blocks that must be echoed with their signature on the next turn [CITED: claude-api skill, csharp tool-use.md: "Signature MUST be preserved - the API rejects tampering"]. Do not support that in this slice: the adapter should fail a `ToolUse` response that contains thinking/redacted_thinking blocks with a typed failure, and the `/eval/decisions` override validation should say which models are supported (or keep the check at the gateway and document it).

### Pattern 4: Cache key v2 and storing tool-use answers

Facts from the code (all read this session): `LlmCacheKey.Version = "llm-cache-key-1"`; `CachingLlmGateway.TryStore` returns false unless `StopReason == LlmStopReason.EndTurn`; `LlmCacheStore.EntryVersion = "llm-cache-entry-1"` and an entry holds only text/stop/usage/cost; `CacheKeyTests` pins both the canonical JSON and the hex for a legacy request and asserts every public `LlmRequest` property is in `KeyedProperties` or `ExcludedProperties`.

Recommendation:
1. Key: `CanonicalJson` writes the legacy shape unchanged (key_version `llm-cache-key-1`) when the request has a document, no system, no tools and no tool turns. Otherwise it writes `key_version: "llm-cache-key-2"` with `document_media_type`/`document_sha256` as null when absent, `system_sha256`, `tools: [{name, description_sha256, schema_sha256}]`, and each follow-up turn as `{role, text_sha256, tool_calls: [{id, name, input_sha256}], tool_results: [{tool_use_id, content_sha256, is_error}]}`. Add the new property names to `KeyedProperties`. The pinned legacy hex test then stays green and the Phase 3 cached extraction runs (`just skeleton 1.00 2 read_only`) keep replaying. A separate pinned vector test covers one v2 request.
2. Store rule: eligible stop reasons become `{EndTurn, ToolUse}`. A `tool_use` answer is a complete, valid completion; refusal and `max_tokens` stay unstored. Update DECISIONS (new entry superseding the D-27 sentence "Only `end_turn` answers are stored").
3. Entry: add an optional `tool_calls` array to `response`; keep reading `llm-cache-entry-1` entries (no tool calls) and write `llm-cache-entry-2`; `key_fields` gains optional `tool_count`/`tool_turn_count` (non-content summary only).
4. Every call in the loop is its own entry. Because the committed case bytes make tool results byte-identical, a rerun reproduces every key. The Tools host therefore must be running in `read_only` replay, and any change to a tool's name/description/schema, to the Decision schema, to the prompt, or to the case files changes the keys (this is exactly the CONTEXT D-04 reversibility note).
5. Tool-call ids are provider-generated (`toolu_...`) and stay in the key on purpose: a `refresh` of step 1 yields new ids, so later cached steps correctly miss rather than being replayed under a different earlier answer.

### Pattern 5: Decision schema export chain

- The existing `Decision(DecisionOutcome Outcome, string Reason)` is in `Invoice.cs` (lines 341-350); `DecisionOutcome` is `Approve, Reject, Escalate`. DOM-01 lists `Decision` as a Domain record. Extend it in place (the single constructor call in `DomainTests.cs:579` must be updated) rather than adding a second `Decision` type. Test `Decision_is_not_reachable_from_the_invoice_schema` asserts the string "Decision" never appears in the invoice schema: keep `Invoice` free of it; any new type names must not break that substring check on the invoice schema (they will not appear there).
- Proposed model-facing shape: `Decision { outcome (DecisionOutcome), reason (string), cause (DecisionCause), evidence (EvidenceItem[]) }`, `EvidenceItem { source, ref, value }` all strings.
- `DecisionCause` should be a required enum with a `none` member (`none, extraction_not_success, policy_warning, over_limit, tool_failed, step_budget_exhausted`). A nullable enum (`DecisionCause?`) exports as the bare literal `true` (unconstrained) under the current `CanonicalSchema.TransformSchemaNode`, because the context type is `Nullable<DecisionCause>` and `IsEnum` is false; I confirmed the raw node `"cause":true` with a probe against the project's `Wire.Options`. A required enum also avoids spending the 16-union budget [VERIFIED: probe output `node for System.Nullable`1[Cause] prop=cause: true`; budget limits CITED in structured-outputs doc: 24 optional, 16 union].
- `tool_failed` and `step_budget_exhausted` are assigned only by code. Either keep them out of the model-facing enum by modelling two types (a model-facing `DecisionDraft` with a 4-value cause and the recorded `Decision`), or leave one enum and tell the prompt which values the model may use. The two-type split keeps the grammar the model sees honest; the planner chooses (see Open Question 4).
- `CanonicalSchema.Export()` is hard-wired to `typeof(Invoice)`: generalise to `Export(Type)` (the transform is already type-agnostic). `SchemaExport` writes two more files (canonical and projected via `ModelSchemaProjector` + `SchemaBudget.EnsureWithin`). The `just` `codegen` variable takes one input and one output: add a second `datamodel-codegen` invocation to a second output file (`decision_generated.py`) so `generated.py` stays byte-identical and `schema-check`'s `git diff --exit-code -- schema python/src/carimbo_models` covers both. `--reuse-model --use-title-as-name` and the enum handling already work for `TaxIdKind` (a `StrEnum` in `generated.py`) [VERIFIED: generated.py:131 `class TaxIdKind(StrEnum)`].

### Anti-Patterns to Avoid

- **Letting the model's turn-1 JSON stand without tools.** The prompt must require tool use and the grader's citation check must catch uncalled sources; do not "fix" it with forced `tool_choice` (400 on Fable 5.1 / Opus 5.5 / Sonnet 5.5 per the project's research).
- **Making "no invoice" a tool failure.** `get_invoice` for a `refused`/`schema_invalid` case must return a normal result stating the invoice is absent, otherwise a legitimate extraction-not-success case ends as `tool_failed` and mis-grades. Only an unknown `case_id` (or a transport failure) is a tool failure (D-03, D-11).
- **Reading case files with the raw `case_id`.** Path traversal (see Security).
- **Embedding the expected label in a served case file.** It would be one tool call away.
- **A second retry layer around the MCP client or tool calls.** D-11: no retry; and no Polly (static test).
- **Changing the legacy cache key shape.** It breaks Phase 3 replays and the pinned `CacheKeyTests` hex.
- **Reusing `ExtractionSettings`/`EvalOverrides` for the agent.** Add separate `AgentSettings` (`MaxSteps`, `MaxTokens`, `Model`, `ToolsUrl`) bounded at startup, with the limit shared with the endpoint like `ExtractionSettings.MaxRepairsLimit`.

## Common Pitfalls

### Pitfall 1: A nullable enum silently loses its constraint
**What goes wrong:** `DecisionCause? Cause` exports as `"cause": true`, so the grammar lets the model emit any value, and codegen yields an untyped field.
**Why it happens:** `CanonicalSchema.TransformSchemaNode` only rewrites a node when `context.TypeInfo.Type.IsEnum`; for `Nullable<Enum>` it is false [VERIFIED: probe].
**How to avoid:** required enum with `none`, or extend the transform to unwrap `Nullable<>`. Add a Domain test asserting the exported Decision schema has an `enum` for `outcome` and `cause` and none is the bare `true`.
**Warning signs:** `schema/decision.schema.json` contains `"cause": true` or `"outcome": true`.

### Pitfall 2: Replay misses because tool-use turns are not cached
**What goes wrong:** `just decisions 1.00 read_only` fails every case with `cache_miss` even after a live run.
**Why it happens:** `CachingLlmGateway` stores only `EndTurn`; the intermediate steps end with `tool_use`.
**How to avoid:** Pattern 4 (store `ToolUse`, entry carries tool calls, key covers the whole conversation). Add a test: live-shaped run in `read_write`, then the same run in `read_only` makes zero inner calls and reproduces the decision byte for byte.
**Warning signs:** step records with `cache.status == "miss"` on a rerun, or `infrastructure_failure/cache_miss` in `read_only`.

### Pitfall 3: Replay needs the Tools host
**What goes wrong:** the replay recipe starts only the Api; `list tools` fails and every case escalates `tool_failed`.
**Why it happens:** tool definitions and tool results are inputs to each request's key; they are read live from the Tools host even when the model answers come from cache.
**How to avoid:** `just decisions` and the e2e fixture start both processes; document it. Do not special-case replay.

### Pitfall 4: Guard depends on the model having fetched the status
**What goes wrong:** a model that answers `approve` from the first turn never called `get_extraction_status`; a status-reading guard has nothing to read and either crashes or skips the override.
**How to avoid:** the guard makes its own recorded MCP call after the model answers (Pattern 2); a guard failure is `tool_failed`.

### Pitfall 5: `IsError` null, tool error text, and unknown tool exception
**What goes wrong:** treating `IsError == false` as the success test misses `null`; treating all failures as `IsError` misses the `McpProtocolException` for an unknown tool and the `HttpRequestException` for an unreachable host.
**How to avoid:** `failed = result.IsError == true` plus catch `McpException`/`HttpRequestException`/`OperationCanceledException` (not a caller cancellation) around the call and around `CreateAsync`/`ListToolsAsync`; record the tool name and a short error class, never the response body. Tool error text for a missing argument is generic; for an `McpException` it echoes the message (keep messages free of paths).

### Pitfall 6: Changing the legacy key or entry format breaks Phase 3 replays
**What goes wrong:** `just skeleton 1.00 2 read_only` and the committed `evals/results` stories stop replaying.
**How to avoid:** Pattern 4 (conditional key version, entry reader accepts v1). Keep `CacheKeyTests` pinned values untouched and add new pinned vectors.

### Pitfall 7: Thinking models and tool turns
**What goes wrong:** `overrides.model = claude-sonnet-5-5` (priced, so accepted) returns thinking blocks in a `tool_use` turn; the next request omits them and is rejected or degrades.
**How to avoid:** Pattern 3 (typed failure on thinking blocks; document supported models). Haiku 4.5 is the default and has no thinking by default.

### Pitfall 8: Tool descriptions and schemas are part of the cache key
**What goes wrong:** a copy edit to a `[Description]` invalidates every recorded run silently.
**How to avoid:** a test pins the SHA-256 of the served tool list (names, descriptions, schemas), like the prompt SHA pins in `ExtractorTests`; the Decision schema SHA is already in the response `effective`.

### Pitfall 9: Live probe cannot be run by the agent
**What goes wrong:** the D-13 spike is silently skipped and the whole loop is built on an unverified combination.
**Why it happens:** no provider key exists in this environment (`CARIMBO_ANTHROPIC_API_KEY` and `ANTHROPIC_API_KEY` both unset) and AGENTS.md allows live calls only through capped `just` recipes.
**How to avoid:** Wave 0 plan: extend `tools/LlmSpike` with an `--agent-probe` mode (budget US$0.10) and a `just agent-probe` recipe (add it to the live-recipe list in `test_live_recipes_resolve_the_key_through_secretspec_and_never_echo_it`), writing `docs/spikes/03-agent-probe.md`; mark it a `checkpoint:human-action` so the user supplies the key. Build everything else offline first. The probe should assert: HTTP 200 with `tools` + `output_config.format`; a tool-using turn returns `tool_use`; the final turn is `end_turn` text that parses as the Decision; whether the model calls tools before answering with the agent-001 prompt.

### Pitfall 10: Per-step system prompt/tools tokens are re-sent every step
**What goes wrong:** cost grows linearly with steps. Haiku 4.5's minimum cacheable prefix is 4096 tokens; the prompt plus four tools will likely be below it, so prompt caching will not help [ASSUMED]. Estimated spend per case is about US$0.01-0.03 (about 3-4 calls of 3-8k input tokens at US$1.00/MTok plus a few hundred output tokens at US$5.00/MTok, from the extraction run data), so about US$0.1-0.25 for 8 cases, well under the US$1.00 cap [ASSUMED estimate].

### Pitfall 11: Generated case bytes must be deterministic
**What goes wrong:** the staleness check flaps (map ordering, culture, float formatting, line endings).
**How to avoid:** serialise with `Wire.Options` and the repo's LF/indent writer, sort cases by id, `InvariantGlobalization` is already on; the generator `--check` compares bytes (as `SchemaExport --check` does).

5. **`prompt_version` override for decisions?** CONTEXT leaves it to the planner. Recommendation: no override in `decision-1` (one pinned `agent-001` prompt, SHA-pinned in a test like D-30); add a catalog later when there is a second prompt.

# Phase 1 Plan 14 (gap closure): typed outcomes for unrepresentable amounts and pattern-violating fields

## Phase Goal

**As a** developer, **I want to** generate a few synthetic DANFEs, extract them live through the .NET eval endpoint and grade the stored results from Python, **so that** the whole measurement loop runs end to end on real code before any breadth is added.

<objective>
Close the two .NET gaps in 01-VERIFICATION.md that break ROADMAP success criterion 4 ("returns either a schema-valid Invoice or a typed refusal, truncation or infrastructure failure"):

1. CR-01 (BLOCKER, EXT-01/EXT-02): a 32-digit `total_amount` makes `Money.Parse` throw `OverflowException`, which escapes the converter and the extractor and becomes HTTP 500 after the paid provider call. Fix it so it is `schema_invalid`, at the Domain layer (no overflow), the converter (defence in depth) and the extractor (narrow value-conversion catches), with regression tests at all three levels.
2. WR-03 (PARTIAL, EXT-01): `[RegularExpression]` on `AccessKey` and `Cnpj` only feeds the exported schema; the serializer ignores it, so `access_key: "bad"` is reported as `success`. Resolution chosen: ENFORCE (not defer). A pure Domain method `Invoice.PatternViolations()` checks every pattern-bearing string member against the same `Patterns` constants the schema is exported from, and the extractor returns `SchemaInvalid` naming the offending JSON paths. A schema-driven test makes drift between the model-facing schema and the enforcement a test failure.

Why enforce rather than document a deferral: EXT-01 and SC4 promise a schema-valid Invoice; Phase 2's requirements (VAL-01..VAL-06) cover check digits and cross-field rules, not schema conformance, so 01-VERIFICATION.md found no later phase that owns it. Enforcement does not conflict with D-03: D-03 limits the access key to the schema's 44-character pattern and rules out check-digit validation in Phase 1. This plan enforces exactly that pattern and adds no check-digit logic. The Domain stays pure: `System.Text.RegularExpressions` is part of the base class library, and `DomainTests.Domain_assembly_references_only_the_base_class_library` keeps guarding it.

Purpose: typed failures are never wrong answers, and success means schema-valid. Phase 2 builds validators and repair on this contract.
Output: fixed `Wire.cs`, `Invoice.cs`, `InvoiceExtractor.cs`; regression tests in `EvalEndpointTests`, `DomainTests`, `ExtractorTests`. No schema, generated-model or package change.
</objective>

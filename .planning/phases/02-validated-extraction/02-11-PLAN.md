# Phase 2 Plan 11 (gap closure): a null list element is a typed schema_invalid, never a validator crash

## Phase Goal

**As a** developer, **I want to** have every extraction target the full DANFE-visible invoice, pass deterministic validators and be repaired within a bounded budget, **so that** extracted invoices carry hard guarantees before anything is measured at scale.

This plan closes VERIFICATION gap 1 (review CR-01): `"items": [null]` or `"installments": [null]` parses with `Wire.Options`, passes `PatternViolations()`, reaches `InvoiceValidator.Validate`, which throws `NullReferenceException`; the exception escapes `ExtractAsync`, `POST /eval/extractions` answers 500 and the already-paid attempts are lost.

<objective>
Reject null where the schema requires a value at the parse boundary (schema_invalid), make the validator total on such input (NULL_VALUE errors, never an exception), and pin both with regression tests at the validator, extractor, repair-loop and endpoint levels.

Purpose: restore the hard guarantees of SC3/VAL-01 ("validators never throw") and SC4/SC5 ("success means schema-valid", every attempt recorded) for a model-reachable input (VAL-01, EXT-04, API-01).
Output: `Invoice.NullViolations()`, the Parse rejection, `RuleIds.NULL_VALUE` with the validator entry guard and its repair sentence, and the regression tests.
</objective>

- `Invoice` (Domain, BCL-only) is a positional record: AccessKey, Number, Series, IssueDate, OperationNature, Issuer (`Party`), Recipient (`Recipient`), Items (`IReadOnlyList<LineItem>`), Totals (`Totals`), Installments (`IReadOnlyList<Installment>`). Only `Party.Ie` and `Recipient.Ie` are `string?`. `Directory.Build.props` enables nullable annotations and warnings as errors.
- `Invoice.PatternViolations()`: reflection walker (private static `Collect`, properties ordered by MetadataToken, snake_case paths with `[i]` indices, `IsDomainRecord` = class in the Domain namespace). It skips null values and null list elements.
- `Wire.Options`: `RespectNullableAnnotations = true` (a JSON null member is a JsonException) but a null collection element deserializes as a null element.
- `InvoiceExtractor.Parse(string text)`: Deserialize with Wire.Options, JSON null gives SchemaInvalid("The model output was JSON null."), then PatternViolations gives SchemaInvalid("The model output does not match the schema pattern of: ..."), else Success. Catches only JsonException, FormatException and OverflowException.
- The loop in `ExtractAsync`: a schema_invalid at index 0 is the outcome; a schema_invalid at a repair index consumes budget and, when the budget is spent, returns the last candidate as ValidationFailed. Every attempt is added to `attempts` with its `LlmResponse`.
- `InvoiceValidator.Validate(Invoice, DateOnly)`: ArgumentNullException for a null invoice, then IdentityRules, KeyAndDateRules (AppendKeyCrossChecks, AppendDates), ArithmeticRules. No catch-all by design (02-04).
- `RuleIds`: public const strings, value equal to name. `Finding.Error(field, ruleId, expected, actual)` (internal).
- `RepairFeedback`: RevealSet (13 arithmetic and date rules) and FixedSentences (every other rule except TAX_CODE_UNSUPPORTED). `RepairLoopTests.Exactly_the_arithmetic_and_date_rules_reveal_values_and_every_other_rule_has_its_own_sentence` reflects over RuleIds, so a new id needs a fixed sentence.

Design choice (planner, per the verifier's two options): the null check lives in the Domain walker, not as a hand-written two-list check in Parse. It is driven by the same reflection as `PatternViolations`, so a list member added later is covered automatically, and any consumer of the Domain can ask whether an invoice is schema-valid. The validator guard is the defence in depth VAL-01 needs for direct callers (ground-truth gate, Phase 4 dataset tool, tests); it reports an error, so it can never mask the schema rejection, and the extractor tests prove Parse rejects first.
